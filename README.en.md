A tiny keyboard that fits under one hand, originally built for osu!-style games that want
short travel and few keys. The MCU is an Arduino Leonardo (ATmega32u4), every key has its own
WS2812B, and everything is configured through the
[KeyboardOG](https://github.com/LGGZi/KeyBoard-OG-key-binding-tool) host tool — no driver, no
serial port, and the keyboard stays a normal composite HID device:

```
host ──(HID Report ID 4, 8-byte commands)──> firmware
     <─(ACK / FIN / query data / device info)─
```

> **No keys are bound by default** — write your mappings with the host tool first.

## Features

### Key scan and debounce

- 6 low-profile switches in 2 rows × 3 columns (`0 1 2` / `3 4 5`); digital inputs with
  internal pull-ups, pressed = low.
- **Press is immediate**; a release needs `release_debounce` ms of continuous release.
  The value lives in EEPROM byte 0, range 1..20 ms (default 1).
- The state bitmap is **latched**: bits change only on transitions, so a key resting between
  thresholds never loses its state.

### LEDs (one WS2812B per key)

- Data pin **D4**, 12 effects in three groups, integer maths only, 10..200 fps:
  - **mono**: off / solid / press / press + afterglow / typing heat / breath / wave /
    sparkle / ripple / comet
  - **rainbow**: rainbow flow / rainbow breathing / rainbow wave / rainbow sparkle /
    rainbow comet
  - **dual colour**: dual breath / dual press / dual press + fade / dual wave / dual comet /
    dual typing / left-right gradient / dual ripple
- Adjustable: **brightness 0..255, speed 1..20, frame rate 10..200 fps, primary and secondary
  colour**; the whole parameter block is stored in EEPROM.
- Ripple / rainbow / wave / gradient use the real **2 × 3 layout** to decide direction.
- Everything can be tuned live from the host; pressing "Save LED" persists it.

### Key mappings

- Up to **12 bindings per key** (matches the firmware's `MAXIMUM_BINDABLE_KEY`), applied in order.
- Mix keyboard / mouse / gamepad / media keys; modifiers are translated to the HID modifier byte.
- Mappings are level-triggered: a held key keeps reporting, releasing clears it.

### Layout upload

- The firmware reports each key's `x / y / w / h` (0.25 u units) so the host can draw the real
  layout and select keys by clicking it (`QUERY_LAYOUT = 0xFE`).
- The table is generated by `kle2c.py` from keyboard-layout-editor data and checked against
  `BUTTONCOUNT` with `static_assert`.

### Firmware version check

- The device-info frame (`0xFF`) carries two versions, both packed as **2 | 3 | 3** bits:

  | Byte | Meaning |
  |---|---|
  | `[6]` | host version this firmware expects (currently `0x47` = 1.07) |
  | `[7]` | firmware version (currently `0x45` = 1.05) |

- The host compares them on connect: if the firmware expects a newer host, the status bar and
  log say so and the version label turns red. The host also keeps a
  "software version ↔ supported firmware range" table.

## Quick start

### 1. Flash the firmware

Open `CODE/6kb/6kb.ino` in the Arduino IDE, select **Arduino Leonardo**, upload.

### 2. Connect the host tool

1. Start [KeyboardOG](https://github.com/LGGZi/KeyBoard-OG-key-binding-tool), click "Refresh",
   and pick your keyboard (only devices that answer the device-info probe are listed).
2. Click "Connect": device info, all mappings and the LED settings are read automatically.

### 3. Write mappings / tune LEDs

1. Pick a key on the left, click the target key on the right (left click replaces, right click
   appends, clicking an existing binding removes it), then press "Write current key".
2. Switch to the "LED" tab: choose group and effect, drag brightness / speed / frame rate,
   pick both colours — changes apply immediately; press "Save LED" to store them.

## Build from source

Libraries: **FastLED** (LED effects) and the bundled **EEPROM**.

Arduino IDE: open `CODE/6kb/6kb.ino`, select **Arduino Leonardo**, upload.

Command line (arduino-cli):

```bash
arduino-cli compile --fqbn arduino:avr:leonardo CODE/6kb
arduino-cli upload  --fqbn arduino:avr:leonardo -p COM5 CODE/6kb
```

Current footprint: ~16.2 KB flash of 28 KB, ~640 B RAM of 2.5 KB.

## Protocol at a glance

Commands and replies use **Report ID 4**, 8 bytes: `[0]` is the command code, `[7]` is an
incrementing host sequence (the firmware drops a command identical to the previous one).

| Command | Value | Meaning |
|---|---|---|
| set mapping | 0x01 | `[1]=device [2]=key [3]=offset [4]=APPEND/OVERRIDE/CLEAR [5]=slot` |
| query | 0x04 | `[1]=0 mapping / 0x03 LED / 0xFE layout / 0xFF device info` |
| ACK / FIN | 0x05 / 0x06 | replies |
| refresh | 0x07 | reload from EEPROM |
| set LED | 0x08 | `[1]=effect [2]=brightness [3]=speed [4..6]=color1` |
| set accent | 0x09 | `[1..3]=color2` |
| save LED | 0x0A | `[1]=0x5A` confirm |
| frame rate | 0x0B | `[1]=fps (10..200)` |

Three things that bite most often:

1. **One command, two replies**: ACK then FIN; reading only one leaves the FIN for the next command.
2. **The device-info frame has no FIN**: end the query when the `0xFF` frame arrives.
3. **The firmware drops duplicate commands**: increment `[7]` every time.

Full byte layouts, reply formats and the EEPROM map are in
[`CODE/6kb/README.en.md`](CODE/6kb/README.en.md) ([中文](CODE/6kb/README.md)).

## FAQ

**Q: nothing happens after flashing**

- No bindings exist by default; write mappings with the host tool first.
- Make sure the board is set to **Arduino Leonardo** (not Micro / Pro Micro).

**Q: the host reports a 3000 ms timeout right after connecting**

- The device-info frame has no FIN; the host must end the query on the `0xFF` frame. Use a
  matching host version.
- Do not keep the Arduino serial monitor open.

**Q: LED settings revert after replugging**

- "Save LED" (`CMD_SAVE_LED`, confirm byte `0x5A`) is what writes EEPROM.
- Old firmware silently ignored the save because the confirm byte did not match its struct
  magic; flash the current firmware.

**Q: brightness is uneven / flickers at low levels**

- That is the WS2812B itself at low levels; the firmware disables FastLED temporal dithering
  and consistently scales with `scale8`.

**Q: can this become a 9-key board?**

- `buttonPins[]` already lists nine pins (`1, MISO, SCK`), but D1 is the serial TX pin — verify
  those pins are actually free on your board.
