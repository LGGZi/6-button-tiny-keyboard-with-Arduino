# Six-key keyboard firmware (6kb)

[中文](README.md) | **English**

This document describes the firmware's **structure, data flow and conventions** for
debugging and for anyone picking the code up later. The Chinese comments in the code
explain *why* something is written that way; this file explains *how it works overall*.

- MCU: ATmega32u4 (Arduino Leonardo core, `arduino:avr:leonardo`)
- Keys: `BUTTONCOUNT = 6`, **plain mechanical switches** (digital input, pull-up, active low)
- One WS2812B per key (data on D4, arranged as 2 rows × 3 columns)
- Firmware version: `FIRMWARE_VERSION` in `Universal.h`, currently `0x46` = 1.06
- Required host version: `HOST_VERSION_REQUIRED` in `Universal.h`, currently `0x47` = 1.07
- Host protocol: Report ID **4**, 8-byte commands (used by the KeyboardOG host tool)

> Relation to the hall-effect version (`rtkb-layout-edited`): the protocol, mapping
> format and EEPROM mapping layout are the same. Differences: no analog scan / rapid
> trigger / calibration, one RGB LED per key, and the debounce time lives in EEPROM.

## 1. Files and responsibilities

| File | Responsibility | Usually changed when |
|---|---|---|
| `6kb.ino` | `setup()` / `loop()`: pins, LED strip, main-loop scheduling | adding work to the loop |
| `Universal.h` | global config: key count, mapping slots, pin table, encoder pins, debounce default, firmware version, `report` | key count, pins |
| `KeyManager.h` | key scan + debounce `getKeyState()`, mapping translation `keyOperation()` | debounce feel, mapping semantics |
| `WS2812BManager.h` | LED effects: parameter struct, EEPROM helpers, 12 effects, frame pacing | adding effects, parameters |
| `EEPROMManager.h` | EEPROM: debounce byte (0) + mapping area + LED area, load at boot | storage layout |
| `HIDcmdHandler.h` | host command parsing, ACK/FIN, query replies, device-info frame | new commands, reply format |
| `LayoutManager.h` | layout table + per-key upload (`0xFE` frames) | new layout (generated by `kle2c.py`) |
| `HID.cpp` / `HID.h` / `SubHID.cpp` / `SubHID.h` | composite HID descriptors and report sending | report structure |

## 2. Startup (`setup()`)

```c
delay(1000);                                   // let USB enumerate
wsInit();                                      // LED strip: FastLED.addLeds + clear
ledParamsGetFromEEPROM();                      // load LED params (writes defaults if invalid)
for (i) pinMode(buttonPins[i], INPUT_PULLUP);  // 6 keys: pull-up input, pressed = LOW
pinMode(ENC_L_A/B, INPUT_PULLUP);              // encoder pins (decoding not implemented, see §9)
debounceGetFromEEPROM();                       // EEPROM[0] -> release_debounce
keyCodeInit();                                 // EEPROM mapping area -> key_map[][][]
```

`keyCodeInit()` only runs at **power-up**; after the host changes a mapping it sends
`CMD_REFRESH`, which calls it again.

---

## 3. Main loop (`loop()`)

```c
reportBufferClear();          // clear the HID report
report.lyAxis = -128;         // park the gamepad left stick
keyOperation(getKeyState());  // scan + debounce -> bitmap -> fill the report
wsTick(buttonbuf);            // LED effects: paced by fps, one FastLED.show() per frame
HIDcmdResponseIfChanged();    // handle host commands (deduplicated)
HIDStateUpdate(2);            // actually send a HID report every 2 iterations
delayMicroseconds(500);       // main-loop tick
```

- The LEDs follow **`buttonbuf` (physical state)**, not the debounced `key_trigger_state`,
  so they light up the moment the switch closes.
- `report` is cleared and rebuilt every iteration, so mappings are level-triggered.
- `lyAxis = -128` is historic behaviour: clearing the report would put the left stick at 0
  (= pushed up), so the neutral value is restored by hand.
- LED refresh is decoupled from the loop: `wsTick()` is limited to `ledParams.fps`
  (default 50 fps) internally, while the main loop runs at roughly 500 µs.

## 4. Key scan and debounce (`KeyManager.h`)

### 4.1 Hardware

```c
volatile uint8_t buttonPins[] = {8,6,12,5,10,9, 1,MISO,SCK};   // only the first 6 are used
```

| Key | Pin |
|---|---|
| 0 | D8 |
| 1 | D6 |
| 2 | D12 |
| 3 | D5 |
| 4 | D10 |
| 5 | D9 |

The trailing `1, MISO, SCK` entries are unused (they exist for a 9-key board). If you raise
`BUTTONCOUNT`, take the first N entries — but check that those pins really have switches.

### 4.2 State

```c
volatile uint16_t buttonbuf = 1;      // physical bitmap (initial value 1, see §9)
static uint16_t key_trigger_state;    // debounced bitmap (this is what the caller gets)
static unsigned long time_Pre[6];     // last time each key was seen pressed
```

### 4.3 Debounce algorithm

```c
read all pins -> buttonbuf bits (HIGH = released, LOW = pressed + record time_Pre)
for each key:
    if the buttonbuf bit is 1      -> set key_trigger_state            (press is immediate)
    else if now - time_Pre >= release_debounce
                                   -> clear key_trigger_state          (release is delayed)
```

- Press: **immediate**. Release: the key must stay released for `release_debounce` ms.
- `release_debounce` defaults to 1 ms, range 1..20, stored in EEPROM byte 0.
- The bitmap is **latched** (`key_trigger_state` is a static), not recomputed each pass.

## 5. Mappings and HID reports (`KeyManager.h` / `SubHID.h`)

### 5.1 `key_map`

```c
uint8_t key_map[BUTTONCOUNT][MAXIMUM_BINDABLE_KEY][2];   // [key][slot][device, offset]
```

- Up to `MAXIMUM_BINDABLE_KEY = 12` bindings per key, applied **in order**.
- A slot with `device == NO_DEVICE(0)` terminates the list.

### 5.2 device / offset semantics

| device | Meaning | offset |
|---|---|---|
| 1 `KEYBOARD` | keyboard | high nibble = index into `keyboardKeys[]`, low nibble = bit |
| 2 `CONTROLLER` | gamepad | button bit (`xboxButtons`) |
| 3 `MOUSE` | mouse | button bit (`mouseButtons`) |
| 4 `MULTIMEDIA` | media keys | bit0 mute / bit1 volume- / bit2 volume+ |

`keyboardKeys[]` is 14 bytes: 13 normal key bytes plus one modifier byte.
`offset = 0x04` → byte 0, bit 4; modifiers are `13*16 + bit` (`208 + bit`).

### 5.3 Reports

`HIDConReport_t` (`SubHID.h`) is the composite report. `keyOperation()` only ORs bits into
it; sending happens in `SubHID.cpp` (Report ID 1/2/3 = gamepad/keyboard/mouse, media keys
are a separate report).

## 6. EEPROM layout (`EEPROMManager.h`)

```
offset 0      debounce time (1 byte, 1..20, default 1)
offset 1      mapping area: BUTTONCOUNT * KEYMAP_SIZE_PER_KEY = 6 * 24 = 144 bytes
              12 slots per key × (device, offset) 2 bytes
offset 145    LED parameters: LEDParams_t (10 bytes, see §8)
total         155 bytes (ATmega32u4 has 1024, ~869 free)
```

- `#define KEYMAP_START_POSITION 1`; the LED area offset is computed, never hard-coded:
  `#define LED_PARAMS_START_POSITION (KEYMAP_START_POSITION + BUTTONCOUNT * KEYMAP_SIZE_PER_KEY)`
- An empty slot is any `device` outside 1..4 (0, 0xFF, stale data).
- A debounce byte outside 1..20 keeps the default (an erased EEPROM reads 0xFF).

## 7. Host protocol (`HIDcmdHandler.h`)

### 7.1 Commands

| Command | Value | Meaning |
|---|---|---|
| `CMD_SET_MAP` | 0x01 | write mapping: `[1]=device [2]=key [3]=offset [4]=APPEND/OVERRIDE/CLEAR [5]=slot` |
| `CMD_SET_PARAM` | 0x02 | **not implemented** (no hall parameters on this board) |
| `CMD_CALIBRATE` | 0x03 | not implemented |
| `CMD_QUERY` | 0x04 | `[1]=0 mapping / 0x03 LED / 0xFE layout / 0xFF device info` |
| `CMD_ACK` / `CMD_FIN` | 0x05 / 0x06 | replies |
| `CMD_REFRESH` | 0x07 | `[1]=0` reload mappings |
| `CMD_SET_LED` | 0x08 | live LED: `[1]=effect [2]=brightness [3]=speed [4..6]=color1 RGB` |
| `CMD_SET_LED_ACCENT` | 0x09 | live accent colour: `[1..3]=color2 RGB` |
| `CMD_SAVE_LED` | 0x0A | persist LED params: `[1]=0x5A` confirm |
| `CMD_SET_LED_FPS` | 0x0B | frame rate: `[1]=fps (10..200)` |

### 7.2 Reply conventions

- **ACK**: `{0x05, command, sequence, 0...}`.
- **FIN**: the received 8 bytes echoed back with `[0]` replaced by `0x06`.
- Query data: `[0]=0x01` (binding) / `[0]=0x0C`, `0x0D` (LED) / `[0]=0xFE` (layout).
- **The device-info frame has no FIN** — receiving it ends the query:

  ```
  { 0xFF, BUTTONCOUNT, hall flag, encoder count, device type, layoutKind,
    HOST_VERSION_REQUIRED, FIRMWARE_VERSION }
  ```

  - `[2]=0x0F` = not a hall keyboard;
  - `[5]=0xFF` = the firmware uploads a layout;
  - **`[6]` = host version this firmware expects** (2|3|3 bits, currently `0x47` = 1.07);
  - `[7]` = firmware version.
- The firmware drops a command identical to the previous one, so the host must increment `[7]`.

### 7.3 Layout upload

`layout_custom[]` in `LayoutManager.h` is a PROGMEM table of `{x, y, w, h, flags}` (0.25 u).
`QUERY_LAYOUT (0xFE)` sends `{0xFE, index, x, y, w, h, flags, seq}` per key, then FIN.
The table is generated by `tools/kle2c.py`; its length is checked against `BUTTONCOUNT`
with `static_assert`.

## 8. LEDs (`WS2812BManager.h`)

Data pin **D4**, 6 × WS2812B, physical layout **2 rows × 3 columns**:

```
0 1 2
3 4 5
```

### 8.1 Usage

```c
// setup()
wsInit();                    // FastLED.addLeds + clear + disable dithering
ledParamsGetFromEEPROM();    // load parameters (writes defaults when invalid)

// loop(), after keyOperation(getKeyState())
wsTick(buttonbuf);           // paced by ledParams.fps, one show() per frame
```

### 8.2 `LEDParams_t` (10 bytes, exactly what sits in EEPROM)

| Field | Type | Meaning |
|---|---|---|
| `magic` | uint8 | `0x5B`, marks valid EEPROM data (change it when the layout changes) |
| `effect` | uint8 | effect id 0..22 |
| `brightness` | uint8 | 0..255 |
| `speed` | uint8 | animation speed 1..20 |
| `fps` | uint8 | frame rate 10..200 (default 50) |
| `color1[3]` | uint8 | primary RGB |
| `color2[3]` | uint8 | secondary RGB |

There is exactly one `ledParams`; modify it through `wsSetEffect / wsSetBrightness /
wsSetSpeed / wsSetFps / wsSetColor1RGB / wsSetColor2RGB` (one field per call).

**Two different constants — do not mix them up:**

| Constant | Value | Purpose |
|---|---|---|
| `LED_PARAMS_MAGIC` | `0x5B` | first byte of the EEPROM struct, validates the data |
| `LED_SAVE_CONFIRM` | `0x5A` | `[1]` confirm byte of `CMD_SAVE_LED` |

### 8.3 EEPROM access

```c
// read: whole struct, validate, then memcpy into the global
EEPROM.get(LED_PARAMS_START_POSITION, temp);
if (ledParamsAreValid(&temp)) memcpy(&ledParams, &temp, sizeof(LEDParams_t));
else { ledParamsSetDefault(); ledParamsSaveToEEPROM(); }

// write: whole struct back (set the magic first)
ledParams.magic = LED_PARAMS_MAGIC;
EEPROM.put(LED_PARAMS_START_POSITION, ledParams);
```

### 8.4 Effects (three groups)

**Mono group (uses color1 only)**

| id | macro | effect |
|---|---|---|
| 0 | `LED_EFFECT_OFF` | all off |
| 1 | `LED_EFFECT_SOLID` | solid |
| 2 | `LED_EFFECT_PRESS` | lit while pressed (default) |
| 3 | `LED_EFFECT_PRESS_FADE` | press + afterglow |
| 4 | `LED_EFFECT_TYPING_HEAT` | typing heat (color1 dim to bright, heats while held) |
| 5 | `LED_EFFECT_BREATH` | breathing |
| 6 | `LED_EFFECT_WAVE` | wave |
| 7 | `LED_EFFECT_SPARKLE` | sparkle |
| 8 | `LED_EFFECT_RIPPLE` | ripple |
| 9 | `LED_EFFECT_COMET_MONO` | mono comet |

**Rainbow group (HSV, ignores the colour parameters)**

| id | macro | effect |
|---|---|---|
| 10 | `LED_EFFECT_RAINBOW` | rainbow flow |
| 11 | `LED_EFFECT_RAINBOW_BREATH` | rainbow breathing |
| 12 | `LED_EFFECT_RAINBOW_WAVE` | rainbow wave |
| 13 | `LED_EFFECT_RAINBOW_SPARKLE` | rainbow sparkle |
| 14 | `LED_EFFECT_COMET_RAINBOW` | rainbow comet |

**Dual-colour group (color1 ↔ color2)**

| id | macro | effect |
|---|---|---|
| 15 | `LED_EFFECT_DUAL_BREATH` | dual breath (triangle phase, full 0..255 range) |
| 16 | `LED_EFFECT_DUAL_PRESS` | pressed = color2, released = color1 |
| 17 | `LED_EFFECT_DUAL_PRESS_FADE` | pressed = color2, that key decays back to color1 |
| 18 | `LED_EFFECT_DUAL_WAVE` | dual wave (columns offset 85, rows 30) |
| 19 | `LED_EFFECT_DUAL_COMET` | dual comet (head color2 → two tail steps → dim color1) |
| 20 | `LED_EFFECT_DUAL_TYPING` | dual typing heat: cool color2 → hot color1, **heats while held** (unlike press + fade) |
| 21 | `LED_EFFECT_DUAL_GRADIENT` | left/right gradient (0 / 127 / 255) |
| 22 | `LED_EFFECT_DUAL_RIPPLE` | dual ripple (delay and decay follow `speed`) |

Implementation rules for the dual group (these avoid the old flicker/colour jumps):

- **The background is always exactly `color1`**: press effects keep a per-key `wsGlow[]`
  amount of color2, so a zero leftover is the pure primary colour at constant brightness.
- **No framebuffer feedback**: colours are computed from `color1/color2` and state only.
- **Breath/wave use their own phase accumulators**, so the endpoints are continuous.
- **Ripple** is single-shot: delay `80-2*speed` ms per cell, decay `1800-50*speed` ms.
  The dual ripple no longer paints a held key with color1 (that made the release jump from
  color1 to color2).
- **Comet** advances its head by elapsed milliseconds and takes its brightness from a
  0/1/2/3-cell distance curve, so the head never jumps a whole cell at a time.
- **Both heat effects** ramp up in small per-frame steps (~0.3 s to full) instead of snapping
  to full. The mono heat now uses the primary colour's brightness instead of `HeatColor()`
  (which is black → red → yellow → white and ignores the configured colour).

Ripple, rainbow, wave and gradient all use the 2×3 layout
(`wsKeyCol / wsKeyRow / wsKeyDistance`), so directions follow the real key positions.

### 8.5 LED commands and query

| Command | Value | Layout |
|---|---|---|
| `CMD_SET_LED` | 0x08 | `[1]=effect [2]=brightness [3]=speed [4..6]=color1 RGB [7]=seq` |
| `CMD_SET_LED_ACCENT` | 0x09 | `[1..3]=color2 RGB [7]=seq` |
| `CMD_SAVE_LED` | 0x0A | `[1]=0x5A` (`LED_SAVE_CONFIRM`) `[7]=seq` |
| `CMD_SET_LED_FPS` | 0x0B | `[1]=fps (10..200) [7]=seq` |

08 / 09 / 0B take effect **immediately but are not persisted**; 0A stores the current
`ledParams` in EEPROM.

**Querying the LED settings**: `CMD_QUERY` with `[1] = QUERY_LED (0x03)`; the firmware
answers with two frames and then a FIN:

| Frame | Value | Layout |
|---|---|---|
| basic | `0x0C` | `[1]=effect [2]=brightness [3]=speed [4]=fps` |
| colours | `0x0D` | `[1..3]=color1 RGB [4..6]=color2 RGB` |

Both frames echo the query sequence in `[7]`. Ten parameter bytes do not fit in one
8-byte report, hence two frames.

### 8.6 Local simulator (`tools/led_sim.py`)

Run it before flashing to see what a change looks like:

```bash
python tools/led_sim.py --effect 18 --frames 60 --fps 50 --speed 8 \
                        --color1 FE0107 --color2 00E6FF --out out
python tools/led_sim.py --list          # list effect ids
```

| File | Content |
|---|---|
| `out/frames.png` | filmstrip (one frame per row, six LEDs) |
| `out/timeline.csv` | per-frame per-LED RGB |
| `out/report.txt` | continuity stats: max channel delta, where it jumps, colours before/after |

A delta of 40 or less counts as smooth; effects with a moving front (ripple, comet) may step
once when the front passes a cell; anything else reporting `JUMP` is a real colour jump.
The simulator mirrors the firmware's integer maths (`wsMix8`, `wsScale`, timing, effect
formulas) — keep both in sync.

### 8.7 Performance and timing

- One `FastLED.show()` per frame (~200 µs for 6 LEDs); FastLED's temporal dithering is off.
- All integer maths: `sin8`, `HeatColor`, `scale8`, `blend` are table/assembly based.
- The only lookup table is the 3-byte PROGMEM comet trail (`wsCometTrail`).
- Animation advances by **time**, not by frame:

  ```c
  wsDt = frame interval, clamped to 8..60 ms
  step = (1 + speed/2) * wsDt / 20     // speed only controls "distance per second"
  ```

  Changing the frame rate therefore changes smoothness, not animation speed; below about
  16 fps the animation slows down instead of jumping.
- **Scale brightness with `scale8()`, never `scale8_video()`**: the video variant never
  reaches zero (that is why afterglow/ripple used to stay dimly lit). Also note that
  `CRGB::nscale8_video(x)` takes an *amount to dim*, not a brightness factor.

## 9. Known pitfalls

1. **`buttonbuf` starts at 1** — before the first scan, key 0 looks pressed; it may flash a
   LED and fire one binding.
2. **`buttonPins[]` has 9 entries, only 6 are used** — the extras are `1, MISO, SCK`;
   D1 is the serial TX pin, do not use it above 6 keys.
3. **The encoder is not implemented** — `ENC_L_A/B`, `TT_ACTIVE_COUNT` and
   `ENCODER_PULSE_TIMES` exist in `Universal.h`, but nothing decodes them in `loop()`.
   Port `EncoderManager.h` from the hall version to enable it.
4. **`LED_PARAMS_MAGIC` (0x5B) is not `LED_SAVE_CONFIRM` (0x5A)** — mixing them silently
   ignores `CMD_SAVE_LED` (that bug shipped once already).
5. **Keep `lyAxis = -128`** — `reportBufferClear()` would otherwise put the left stick at 0.
6. **Mappings are level-triggered** — the report is rebuilt every iteration, so a held key
   keeps reporting and a release needs no extra command.

## 10. Symptoms → where to look

| Symptom | Check first |
|---|---|
| a key is always pressed | pin shorted to ground / `release_debounce` too large / wrong pin table |
| a key never reacts | `key_map` empty (EEPROM never written) / pin not `INPUT_PULLUP` |
| sticky release | `release_debounce` too large (default 1 ms, range 1..20) |
| LEDs completely dark | `wsInit()` called? D4 wired? `ledParams.brightness == 0`? |
| afterglow/ripple never turns off | brightness scaled with `scale8_video` instead of `scale8` |
| LED settings lost after replug | `[1]` of `CMD_SAVE_LED` must equal `LED_SAVE_CONFIRM` (0x5A) |
| host reports a 3000 ms timeout right after connecting | the device-info frame has no FIN; end the query on the 0xFF frame |
| layout does not show up | device info `[5]` must be `0xFF`, table length must be 6 |
| mappings require a replug | `keyCodeInit()` only runs in setup and on `CMD_REFRESH` |

## 11. One-page cheat sheet

```
setup: LEDs (wsInit -> ledParamsGetFromEEPROM) -> pins (pull-up) -> debounceGetFromEEPROM -> keyCodeInit
loop : clear report + lyAxis -> getKeyState (scan/debounce) -> keyOperation -> wsTick -> commands -> send -> 500us

keys : digitalRead (pull-up) -> buttonbuf (physical) -> key_trigger_state (latched)
       -> keyOperation() looks up key_map -> report -> HIDStateUpdate(2) sends every 2 loops

EEPROM: [0] debounce  [1..144] mappings  [145..154] LED params (LEDParams_t)
cmds  : Report ID 4, 8 bytes; ACK=0x05, FIN=0x06, query data 0x01/0x0C/0x0D/0xFE, device info 0xFF
```
